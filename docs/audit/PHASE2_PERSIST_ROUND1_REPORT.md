### `app/(app)/sessions/[id]/page.tsx` — session detail page

Server component. Fetches `TrainingSession` via `prisma.trainingSession.findFirst`
with `checkIn`, `workoutPlan`, `workoutFeedback`, `stravaLinks` included
(`app/(app)/sessions/[id]/page.tsx:65-76`). Renders in sections:

- **A: Session chips** (`:195-222`) — intensity, duration, slot, planning-type,
  intent label. This is the natural home for `distanceKm` / pace / HR-zone /
  subtype chips.
- **B: Coach overview** (`:225-254`) — reads `session.workoutPlan` (the
  `SessionWorkoutPlan` relation), shows `plan.goal`, `plan.target`,
  `plan.planType`, `plan.summary`, and the athlete's computed HR zones
  (`buildHrZones(trainingProfile)`).
- **C: Workout blocks** (`:257-301`) — also from `session.workoutPlan.blocks`.
- Title (`:180`) falls back to `session.notes ?? dateStr`.

**Confirmed: `SessionWorkoutPlan` is a separate concern, not a duplicate.**
`session.workoutPlan` (`SessionWorkoutPlan` model, `prisma/schema.prisma:330-348`)
is populated by a *different* LLM call — `lib/ai/workout-plan.ts`, triggered
on-demand via `POST /api/sessions/[id]/workout-plan` ("Plan workout" button in
`session-card.tsx`), not by the weekly planner. Its `target: String?` field
(`lib/ai/workout-plan.ts:497-499`) is a free-text label like `"10 km at Z2"` or
`"3 rounds × 8 stations · 60s work / 20s transition · RPE 5–6"` — for hybrid
sessions it's built deterministically from block math
(`lib/ai/workout-plan.ts:453`), for others it's LLM-generated prose. It exists
to describe a detailed on-demand workout breakdown, generated only if/when the
user asks for one.

The four fields in this task come from a *different, earlier* call — the
weekly planner's `submit_plan` tool output (`ClaudeAdapter.generatePlan`,
called from `generateWeeklyPlan`/`generateNextWeekDraft` in
`lib/planner/orchestrator.ts`) — and are numeric/structured (`distanceKm: number`,
not a formatted string). They represent what Claude decided *when generating
the session*, before any on-demand plan exists. A session can have these
fields populated with no `SessionWorkoutPlan` row at all (most sessions never
get "Plan workout" clicked).

**Conclusion: clearly separate concerns, no duplication/confusion risk.**
`TrainingSession.{distanceKm,...}` = generation-time snapshot (always present
if Claude supplied one). `SessionWorkoutPlan.target` = on-demand detailed
breakdown (present only when generated, string not numbers). Proceeding with
the placement as specified.

## 2. Design decision

Adding directly to `TrainingSession` (`prisma/schema.prisma:206-227`) as
additive nullable columns, mirroring `PlannedSession`'s shape
(`lib/ai/adapter.ts:149-164`) exactly:

```prisma
distanceKm          Float?
targetPaceMinPerKm  String?
targetHrZoneMin     Int?
targetHrZoneMax     Int?
subtype             String?
```

`targetHrZone: { min: number; max: number }` on `PlannedSession` is split into
two flat `Int?` columns (`targetHrZoneMin`/`targetHrZoneMax`) rather than a
`Json` column — matches the existing pattern on this model (no other JSON
columns on `TrainingSession`; `WeekSummary.signals` is the only precedent for
JSON elsewhere and that's a genuinely variable-shape bag, this isn't) and
keeps both fields queryable/typed.

No alternative placement considered better — going with the spec as given.

### Generated migration SQL (full, unedited)

```sql
-- AlterTable
ALTER TABLE "TrainingSession" ADD COLUMN     "distanceKm" DOUBLE PRECISION,
ADD COLUMN     "subtype" TEXT,
ADD COLUMN     "targetHrZoneMax" INTEGER,
ADD COLUMN     "targetHrZoneMin" INTEGER,
ADD COLUMN     "targetPaceMinPerKm" TEXT;
```

**Confirmed additive-only**: single `ALTER TABLE ... ADD COLUMN` statement, 5
nullable columns, no `DROP`, no `NOT NULL`, no destructive `ALTER`, no other
statements.

Note: `prisma/migrations/` is covered by `.gitignore`'s `*.sql` rule (intended
to keep ad-hoc DB dumps like the backup file out of git), so — same as the
prior `20260913150000_...` migration on `main` — the migration.sql was staged
with `git add -f`, force-adding only that one file. The backup dump was left
untracked and unstaged.
