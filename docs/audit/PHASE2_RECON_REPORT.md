## 3. File summaries

### `lib/ai/claude-adapter.ts`
- **Input:** `PlanningContext` (from `lib/ai/adapter.ts`) — user, goals, `goalGuidance`,
  availability windows, schedule events, previous week's sessions, recent/this-week check-ins
  (with `category`: injury/fatigue/ok and `resolvedAt`), `currentWeekDoneSessions` (with optional
  `executionDelta`), `fixedSessions`, `optionalSlots`, `safetyBlockedSessions`, `weeklyReview`
  (incl. parsed family constraints), `parsedPreferences` (day requests / desired / sacrificed
  modalities / availability hints), `readinessSummary`, `weekHistory` (last 4 `WeekSummary` rows),
  `replanReason`.
- **Output:** `PlanResult { focusSummary: string, sessions: PlannedSession[] }` where each session
  is `{ scheduledDate: Date, preferredSlot, planningType, durationMin, intensity, notes }`.
- **What it does:** builds one giant JSON prompt (`buildUserPrompt`) plus a long, rule-laden
  system prompt, and calls Claude (`claude-sonnet-4-6` default, override via
  `ANTHROPIC_MODEL`) with a single forced tool call `submit_plan` (`tool_choice: {type:"tool"}`),
  `max_tokens: 2048`. It is a single non-streaming, single-shot call — no retries, no partial
  fallback, no critique/repair loop. Output shape is exactly the tool's `input_schema`: enum-only
  `intensity` (easy/moderate/hard), enum-only 4 modalities baked into prose (not schema-enforced),
  free-text `notes` field is the only place distance/subtype/pace lives (unstructured). The system
  prompt is huge (~260 lines) — most of Phase-2-relevant behavior (goal weighting, taper, injury
  windows, readiness, weekly review priorities, execution deltas) is encoded as **prose
  instructions to the LLM**, not as typed schema fields the LLM must fill in — i.e. richer signals
  exist in the prompt but the *output* schema is still just 6 flat fields per session.

### `lib/planner/orchestrator.ts`
- Two entry points:
  - `generateWeeklyPlan(userId, replanReason?, weeklyReview?)` — used by both "Generate plan"
    (`POST /api/plans`, no reason) and "Replan" (`POST /api/plans/replan`, with reason +
    optional weeklyReview). Archives current active plan, creates a new active plan for
    *this* week, carries forward done/skipped/manual sessions untouched, calls
    `ClaudeAdapter.generatePlan`, applies deterministic rules (`applyRules`, `filterSessions`,
    `deduplicateSessions`) and an injury safety override computed in code (not LLM), then writes
    everything in one `prisma.$transaction`.
  - `generateNextWeekDraft(userId, weeklyReview?)` — used by the weekly-review flow. Builds a
    **draft** (`status: "draft"`) for *next* week, incorporating `weekHistory` (last 4
    `WeekSummary`), `PlannedFixedSession` rows, parsed free-text preferences
    (`parseLLMPreferences`) enforced deterministically post-hoc
    (`enforceExplicitPreferences`), and stamps `consumedByPlanId` on `PlannedFixedSession` rows
    that survived into the persisted plan.
- **Inputs assembled:** goals, availability windows, schedule events, previous/this-week
  sessions + check-ins (categorized injury/fatigue/ok via `categorizeCheckIn`), recurring
  sessions split into fixed vs. optional, Strava-derived `executionDelta` per done session,
  `computeGoalGuidance` output, `WeekSummary` history, `readinessSummary`
  (`DailyReadiness`), parsed family constraints (Haiku call) and parsed training preferences.
- **Outputs:** a `TrainingPlan` row (active or draft) + its `TrainingSession` children, written
  transactionally; deterministic `focusSummary` fallback (`buildDeterministicFocusSummary`) is
  always computed and an LLM-authored `changeExplanation`/draft narrative is layered on top via
  `lib/ai/coach-advice` (`renderChangeExplanation` / `renderNextWeekDraftSummary`) — a **second**
  Claude call, separate from the plan-generation call.
- Injury safety windows, weekly volume caps, and rest-between-hard-session rules are all
  enforced in code post-generation (`lib/rules/*`), not trusted from the LLM output alone — this
  is the "rules engine + LLM hybrid" from CLAUDE.md, still intact.

### `lib/planner/rollover.ts`
- **Input:** `userId`, `todayStr`.
- **Output:** `boolean` (whether a rollover happened).
- **What it does:** `activateDraftIfReady` — finds the latest `draft` plan; if its `startsAt` has
  arrived, archives *all* currently-active plans for the user (defensive against a multi-active
  edge case) and activates the draft, in one transaction. Then, best-effort and **outside** the
  transaction, computes and persists a `WeekSummary` for the plan just archived
  (`persistWeekSummary`), idempotent via the `@@unique([userId, weekStart])` constraint. Called
  opportunistically from any page needing fresh plan data (not a cron) — matches "no cron" MVP
  constraint carried into Phase 1.

### `lib/planner/goal-guidance.ts`
- **Input:** `GoalGuidanceInput[]` (id, title, discipline, targetDate as `YYYY-MM-DD` or null,
  priority 1-3 or null) + `todayStr`.
- **Output:** `GoalGuidance { primaryFocus, perGoal: PerGoalGuidance[], taperGoal }`, each
  `PerGoalGuidance` carrying a normalized `weight` (sums to ~1), a derived `phase`
  (base/build/taper: taper ≤14 days, build ≤56 days, else base), and `daysUntil`.
- Pure, framework-agnostic function shared between the orchestrator (feeds the LLM prompt) and
  the Goals page UI (renders the same weighting for the user) — good example of one computation
  driving both server prompt and client display.
- Weighting formula: `priorityFactor (P1=3, P2=2, P3=1, unset=1) × proximityMultiplier`
  (≤14 days → 2.5×, ≤56 days → 1.6×, else 1×), normalized. This is the entirety of "goal-driven
  prioritization" logic — deterministic, not LLM-computed, then handed to the LLM as guidance the
  system prompt says to bias volume/specificity toward.

### `lib/dossier/types.ts`
- Declares `AthleteDossierFacts` as an **optional-everything** TypeScript type: `maxHr`,
  `lthrEstimate`, `weightKg`, `unavailablePatterns: string[]`, `failureHistory:
  {date,cause}[]`, `gear: Record<string,string>`, `protocols: {name,adoptedAt,rule,rationale}[]`.
  This is the only place the shape is declared — it is a **type-only** contract, not a Zod/Prisma
  schema, and nothing enforces it at runtime (see §5).

## 4. "Generate plan" button flow on `/week`

- `app/(app)/week/page.tsx` renders `<ReplanButton mode="generate" />` (line 274).
- `components/replan-button.tsx`: `mode="generate"` → `POST /api/plans`; `mode="replan"` →
  `POST /api/plans/replan`.
- `app/api/plans/route.ts` (POST): auth check, 30s cooldown (`checkCooldown("plans:generate")`),
  calls `generateWeeklyPlan(userId)` with no reason/review, returns the plan JSON or 500 on
  error. No request body is read at all for "Generate plan" — it's parameterless.
- `generateWeeklyPlan` (see §3) queries the current active plan, all planning inputs, calls
  `ClaudeAdapter`, filters/dedupes, and in **one `prisma.$transaction`**:
  1. archives the previous active plan (`status: "archived"`) if one exists,
  2. creates the new plan with `status: "active"`,
  3. moves done/skipped sessions and user-created manual-planned sessions onto the new plan
     (`updateMany` on `planId`),
  4. creates the new `TrainingSession` rows for `validSessions`.
- **Archive-first invariant — confirmed respected at every write site.** Full grep of
  `status: "active"` (or the equivalent Prisma `where`/`data` shape) across `app/`, `lib/`,
  `components/`:
  - **Writers of `TrainingPlan.status = "active"`** (the ones that matter for the invariant):
    - `lib/planner/orchestrator.ts:630` — inside `generateWeeklyPlan`'s transaction; archives
      `activePlan` (read at line 328, `orderBy: createdAt desc`) *before* creating the new active
      plan. Correct order, same transaction.
    - `lib/planner/rollover.ts:45-51` — `activateDraftIfReady`; `updateMany` archives **all**
      currently-active plans, then activates the draft, both in the same transaction. Correct
      order (defensive against multiple stray actives).
    - `app/api/plans/import/route.ts:207-217` — `updateMany` to archive active plans, then
      `create` the imported plan as active, same transaction. This is exactly the fix landed in
      the most recent commit (`eac4401 fix(plans): archive prior active plan on import`) —
      confirmed present and correctly ordered.
  - **Readers only** (no invariant risk): `app/(app)/week/page.tsx:189`,
    `app/(app)/today/page.tsx:156,181`, `app/api/plans/archive/latest/route.ts:11`,
    `app/api/plans/review/stats/route.ts:11`, `app/api/readiness/route.ts:72`,
    `app/api/sessions/manual/route.ts:42`, `app/api/sessions/[id]/checkin/route.ts:126,137`,
    `lib/planner/orchestrator.ts:329` (read), `365`/`697` (these are `Goal.status: "active"`, a
    *different* enum on a different model — not a plan-activation site, flagged here only to
    avoid a false match).
  - **Draft creation** (`generateNextWeekDraft`, orchestrator.ts:998-1002) archives other
    **drafts** (`status: "draft"` → `"archived"`) before creating a new draft, but does *not*
    touch the currently active plan — correct, since a draft isn't active until rollover
    promotes it (`rollover.ts` is the sole path that activates a draft, and it archives
    incumbent actives at that point).
  - **Conclusion: no call site creates or flips a plan to `active` without archiving the prior
    active plan first, in the same transaction.** The invariant holds everywhere it's exercised.

## 5. `AthleteDossier.facts` — declared type vs. actual enforcement

- No live DB access in this environment (Supabase MCP connector requires auth I can't complete
  non-interactively), so this is based on the API and type code, which is authoritative for
  "what shape can the app actually produce."
- `app/api/dossier/route.ts`:
  - `GET` returns `{ facts: dossier.facts, version }`, or `{ facts: {}, version: 0 }` if no row
    exists yet — `facts` defaults to an empty object, not an object matching
    `AthleteDossierFacts`'s optional fields.
  - `PUT` accepts **any** JSON object as `facts` (`typeof b.facts !== "object"` is the only
    check) and writes it verbatim, bumping `version`. **There is no runtime validation against
    `AthleteDossierFacts` anywhere** — no Zod schema, no manual key/shape check. `lib/dossier/
    types.ts` is a compile-time-only contract that nothing in the write path imports or checks.
- **Drift risk, concretely:** a client (or a future Phase 2 dossier-writing code path, e.g. an
  LLM-authored dossier update) can write arbitrary keys/shapes into `facts`, and the declared
  type would silently stop reflecting reality. I found no other reader of `facts` besides the
  GET route (no planner code currently reads `AthleteDossier` at all — see next point).
- **Bigger finding: `AthleteDossier` is not wired into planning yet.** Neither
  `lib/planner/orchestrator.ts` nor `lib/ai/claude-adapter.ts` references `athleteDossier` or
  `AthleteDossierFacts` — the dossier is CRUD-only via `/api/dossier` and the review-page editor,
  not yet consumed by `generateWeeklyPlan`/`generateNextWeekDraft`. If Phase 2's premise is that
  the dossier informs planning, that wiring does not exist yet.

## 7. Old orchestrator behavior vs. what Phase 2 apparently needs

Because the master doc (`12_CURRENT_STATE_AND_PHASE2_MASTER.md` §3) wasn't available, this
section is derived purely from reading the orchestrator/adapter code — it names the concrete
mechanisms behind each rigidity called out in the task prompt, so it can be cross-checked against
the real doc once available, rather than restating philosophy I haven't read.

- **Fixed session count:** the `submit_plan` tool description literally says "4–6 sessions
  covering the 7-day week" and the system prompt hardcodes "Default target is 4–5 training
  sessions per week... 6 sessions is allowed ONLY when...". Session count is a prompt-level
  target, not derived from athlete state (fitness, current block, actual weekly capacity) — it's
  the same 4–6 band regardless of who the athlete is or what block they're in.
- **Enum-only distances / no structured pace-distance fields:** `PlannedSession` /
  `submit_plan`'s schema has no `distanceKm`, `paceTarget`, or structured workout-block fields.
  All of that lives in a free-text `notes` string the prompt tells Claude to format as
  `"<modality>: <subtype and brief detail>"`, with a long list of prose rules about which of 4
  fixed distances (5/10/15/21 km) to use. Nothing downstream (rules engine, dedup, DB schema)
  parses or validates that text — `SessionMetrics` (the FIT-derived actuals side) has real typed
  distance/pace fields, but the **planned** side has none, so planned-vs-actual can't be compared
  structurally, only by a human reading `notes`.
- **RPE-only intensity:** `SessionIntensity` enum is exactly `easy | moderate | hard`, mapped in
  the prompt to RPE bands (4-5 / 6-7 / 8-9) but never persisted more granularly — no target HR
  zone, no pace zone, no duration-in-zone. `TunableDefaults.hrDisciplinePct` /
  `efStopThresholdPct` suggest HR/EF-based session control was intended (they parallel
  `SessionMetrics.efWhole/efFirstHalf/efSecondHalf/decouplingPct` on the actuals side) but, per
  §6, none of that is wired into planning — the loop from "how did the session actually execute
  physiologically" back into "how should the next planned session be constrained" doesn't exist
  yet on the planning side, only on the analytics side.
- **No cross-week continuity beyond a shallow trend feed:** `weekHistory` (last 4 `WeekSummary`
  rows, oldest→newest) is passed into `generateNextWeekDraft` only, not `generateWeeklyPlan`
  (i.e. a same-week replan never sees multi-week history, only a next-week draft does). Even
  where present, it's summarized to `{weekStart, adherenceByCount, hardDone/hardPlanned,
  avgFeelScore, mainLimiter, carryForward}` — coarse aggregates, not actual session-by-session
  progression (e.g. no sense of "long run distance progression" or "HYROX pacing trend" across
  weeks; `SessionMetrics` per-session physiological trend data is never rolled up into
  `WeekSummary` or passed to the LLM at all). So even the one continuity mechanism that exists is
  one level too coarse to drive real progressive overload decisions.
- **Two separate LLM calls per plan, not unified:** plan generation (`ClaudeAdapter.generatePlan`)
  and the narrative layer (`renderChangeExplanation`/`renderNextWeekDraftSummary` in
  `lib/ai/coach-advice`) are two independent Claude calls; the "reasoning" the second call does
  about *why* the plan changed doesn't feed back into or get double-checked against the first
  call's actual output beyond the deterministic diff payload built for it. There's no single
  place where the model reasons end-to-end about the whole week with full judgment — the
  judgment is split between prose rules baked into one prompt, deterministic post-filters
  (`lib/rules/*`, `enforceExplicitPreferences`, `deduplicateSessions`), and a second explain-only
  call.
